## Sub-task 1 — Package

### 1.1 How we interpret it

| Phrase | Our interpretation |
|---|---|
| "the artifacts needed for retained claims" | Not everything we have: what a reviewer needs to check the claims the paper keeps. DK-05 established which numbers are reproducible at all, so the package targets exactly those. |
| "analysis scripts" | The recomputation that reimplements the paper's definitions, plus the corrected frontier module and its tests. |
| "pinned dependencies" | Here the honest answer is *none*: everything runs on Python 3.9+ and the standard library. That is stated rather than padded with a requirements file listing nothing — and it is now checked by parsing every packaged module's imports, not taken on faith. |
| "seeds/configuration" | Already inside the evidence archive's study manifests (seed lists, timeout, pass rule, excluded seed). The package carries them rather than restating them. |
| "expected outputs" | Exact counts a reviewer can compare against, including the one discrepancy and the skip count — not "should pass". |
| "step-by-step reproduction instructions" | Two commands, runnable from the package root, with the output they produce. |
| Built, not hand-assembled | A script builds it, so it can be rebuilt identically and every anonymisation is logged. |

### 1.2 What we did

| Step | Action |
|---|---|
| 1 | Took DK-05's list of reproducible claims as the specification for what the package must support. |
| 2 | Wrote `make_supplement.py`, which stages the files, applies each anonymisation with a log line, writes a per-file SHA-256 manifest, and builds a deterministic ZIP (fixed timestamps, no owner or group metadata). |
| 3 | Built **two variants**: `scripts` (code and instructions only) and `full` (code plus the evidence archive). |
| 4 | **Unzipped the result into a clean directory and ran both documented commands**, as a reviewer would. |
| 5 | Fixed what that run exposed, twice, and re-ran until the package worked from inside itself. |
| 6 | Re-ran with the published scorers made available, to confirm the skipped tests do pass when they can run. |

### 1.3 Results and analysis

| Variant | Size | Contents | Reproducible offline? |
|---|---|---|---|
| `scripts` | **0.01 MB** | recomputation, corrected module, tests, README, manifest | No — needs the evidence archive, which the README says plainly |
| `full` | **0.48 MB** | the same plus the evidence archive (27 files) | **Yes** |

Both are far inside the 100 MB limit.

**Running the package found two defects that building it could not.**

1. The test suite loaded the published scorers from a **repository-relative path** that does not exist inside the supplement. A reviewer's first command would have ended in `FileNotFoundError`. The suite now resolves them from `AI_LEVEL_VERIFIERS` or a bundled copy and **skips visibly** when neither is present.
2. The corrected module is **renamed** in the package, and the test still loaded it under its old name. Same symptom, second cause.

**Reviewer-run output, from the packaged copy:**

```
$ python3 analysis/recompute.py --dataset evidence
52 of 53 reported values reproduce from the archive.
132 of 132 cells agree
$ python3 -m unittest analysis/test_frontier_cumulative.py
Ran 15 tests … OK (skipped=7)
$ AI_LEVEL_VERIFIERS=<verifiers> python3 -m unittest analysis/test_frontier_cumulative.py
Ran 15 tests … OK
$ cd evidence && python3 tools/validate.py          # the archive's own tool
{"hsc_episodes": 48, "regime_switch_episodes": 24, "errors": []}   exit 0
```

**Analysis.**
1. **A package that has only been built has not been tested.** Both defects were invisible in the build — the ZIP was well-formed, the right size and fully anonymous — and both would have hit the reviewer on the first command. This is the same failure mode as DK-03's clean build log hiding three empty-looking sections.
2. **Seven skips are the honest outcome**, not a workaround. Those tests compare the corrected frontier against the published scorer, which the package deliberately does not carry. The README states the skip count so a reviewer knows what to expect, and states the one environment variable that turns them on.
3. **The `scripts` variant exists because of a constraint, not a preference.** It needs no rights decision, but it cannot be reproduced offline — so shipping it would mean either omitting a reproducibility claim or making one we cannot support. The README says which.

## Sub-task 2 — Honesty

### 2.1 How we interpret it

| Phrase | Our interpretation |
|---|---|
| "document unavailable/private dependencies and costs honestly" | Name what is missing, in the package itself, where a reviewer reads it — not only in our internal records. |
| "do not claim anonymous reproducibility if private repository access is required" | The `full` variant needs no private access and says so. The `scripts` variant does need a separately distributed archive, and its README states that it therefore **does not** claim anonymous reproducibility. |
| "keep development examples distinct from protected evaluation instances" | Count which items ship with their answers and state the counts in the package, rather than asserting a separation. Where the separation does not hold, say so in the package instead of claiming it does. |
| "exclude credentials, confidential records and private answer keys" | Scan for them rather than assume their absence. |

### 2.2 Results and analysis

**What the package says is missing** (in its own README, not just here): the scoring utility behind the harness-curve figures; the item generators, reference solvers and specification–key tests; two of the three harness-scaling curves; and the record of one of the two library audits.

**Costs.** Everything runs offline on the standard library: no API key, no network, no GPU, no cost. Stated in the README's first paragraph.

**Credentials and keys: none present.** A scan of every file in the evidence archive for `api[_-]key`, `secret`, `token`, `password`, `salt`, `answer_key`, `hidden_.*key` and `credential` returned only metric column names — `input_tokens`, `cache_read_tokens`, `tokens_in`, `tokens_out`. No secret, no evaluation salt, no private answer key.

**Development versus certification: the separation the clause asks for does not hold in the `full` variant.** We first wrote that the README "states that public forms and labelled development keys are development material" — a sentence, not a measurement. Counting the items instead gives a different picture:

| Item corpus inside the `full` variant | Count |
|---|---|
| Items in the inherited benchmark archive | 2,978 |
| Marked `certification_ready` | 824 |
| **Of those, shipping with their own answer material** | **824 — all of them** |
| Development items (not certification-ready) shipping with answers | 618 |

The package now states these counts in its own README, under a heading that says what they mean — the certification-ready items are **disclosed**, not a sealed evaluation set, so a score obtained by a system holding this file is not evidence of capability. Every one of the 824 certification-ready items carries `verifier`, and 484 of them also carry a populated `expected_json`, plus `expected_H`, `expected_max_CID` and `expected_difficulty_json` on the H, C and T families. So the `full` supplement would publish, under CC BY 4.0, the expected answers and the verifier identity for every item the corpus itself flags as certification-ready.

**The owner has already taken a public position on this, which we should have quoted before raising it.** `PUBLICATION_NOTES.md`, known issue 6: *"Descriptions of hidden witnesses or certification protocols in public forms are specifications, not protected instances. Explicitly labelled development keys, including `hidden_defect_key_dev_public`, are public reference material, never secure certification answers."* That is the same conclusion this count reaches from the other direction — the items are disclosed reference material, not a sealed set — and it means the decision below is a licensing question rather than a discovery that something protected has leaked. Raising it without that quotation made it sound like news; it is a confirmation, measured rather than asserted.

Two things this is **not**. It is not a credential leak — no secret, key or salt is present. And it is not us disclosing something closed: the archive is already inside the owner's own public release of 2026-09-17, so the material is public today. What changes is the licence and the audience. Re-publishing it as a TMLR supplement puts those answers under CC BY with a paper that uses the same items for certification, which is the collision the sub-task's wording is aimed at.

**Analysis.**
1. **The check I nearly recorded was a false negative.** The corpus stores these flags as the *strings* `"True"`/`"False"`, not JSON booleans, so an `is True` comparison matched nothing and reported a clean separation — zero certification-ready items with answers. Two of my own counters disagreeing in the same output is what exposed it. The audit script now routes every flag through one `truthy()` helper, with a comment saying why.
2. **The weakest point of the whole package is not a missing file but a sentence.** It would be easy to write "the data is available online" and let a reviewer assume reproducibility. The `scripts` variant's README says the opposite in as many words, because the alternative is a reproducibility claim we cannot support. The development-versus-certification sentence above was the same kind of sentence, and counting replaced it.

## Sub-task 3 — Evidence and anonymity

### 3.1 How we interpret it

| Phrase | Our interpretation |
|---|---|
| "anonymous" | Checked, not assumed: every file *and every entry of every nested archive* scanned for author names, institution, repository names and our own internal task identifiers. A finding fails the build. |
| "no larger than 100 MB" | Measured, both variants. |
| "verified rights to included materials" | We cannot verify them — the release carries no licence. So this is the one part of DK-07 that is **not complete**, and it gates which variant may ship. |
| "filenames, metadata, embedded links and archive contents" | Four separate checks, including ZIP entry metadata and the nested dependency archive. |

### 3.2 Results and analysis

**The archive's own README named an author.** Its Citation section read "Yang, Chengshuai. *Measuring the Unified Intelligence Level…*, Version 2.0, August 2026" — a direct identity leak inside a file that would otherwise have shipped untouched, and an older title as well. The builder replaces that section with "Withheld for anonymous review" and logs the substitution.

**The archive's manifests carried git commit ids.** `manifest.json` recorded `paper.repository_commit` and `studies.harness_scaling_curve.runtime_source_commit`, and the HSC study manifest recorded a third. A commit id is a precise pointer: searched on a hosting service it names the repository it came from, and therefore its owner — a stronger identifier than a name, and one the earlier scan missed entirely because it looked for names and repository *strings*, not hashes. Neither id resolves in this clone, so they come from a private or rewritten history and we cannot test where they lead; nothing in the package reads either field. The builder replaces all three with `withheld for anonymous review`, and the scanner now matches any `*_commit` field so a rebuild cannot reintroduce one.

**Our own file and task names were also identifying.** The working files carry `DK-05`, `DK-06` and the path `tmlr-prep`, and the public repository contains a task file named after the author — so those strings are searchable and point straight back. The builder renames them: `analysis/recompute.py`, `analysis/frontier_cumulative.py`, `analysis/test_frontier_cumulative.py`.

**Scan result: clean.**

| Check | Result |
|---|---|
| Author names, institution, repository names, internal task identifiers | 0 findings across every file |
| Git commit ids | 3 found and withheld; scanner now fails the build on any `*_commit` field |
| Nested archive (`HIL_Coordinate_Benchmark_Datasets_v1_2.zip`) — entry names and every text entry | 0 findings |
| File names | 0 findings |
| ZIP entry metadata | Fixed timestamps (1980-01-01), mode 644, no owner or group |
| Embedded links | One URL, three occurrences: the JSON Schema draft identifier `https://json-schema.org/draft/2020-12/schema`, in two schema files and the line of `validate.py` that checks it. A standards identifier, not a locator — **0 links to an author, institution or repository**. The `scripts` variant contains no URL at all. |
| Size | `scripts` 0.01 MB, `full` 0.48 MB — both far inside 100 MB |

The scanner distinguishes our authors from third parties with the same surname, so "John Yang" (SWE-bench) and "Xueguang Ma" (MMLU-Pro) are not reported. It also requires word boundaries on surnames — without that, "Ting" matches "supporting", "routing" and "accounting", and the scan produced 24 false findings on the first run.

**The package failed the archive's own validator, and had done so since the first build.** The evidence archive ships `checksums.sha256` and a `tools/validate.py` that checks it. Anonymisation edits files that list — the README, and now two manifests — so the validator reported `checksum mismatch` and exited 1. A reviewer running the archive's own tool would have seen a package that looks tampered with. **This was true of the package already committed to this PR**, which fails on `README.md` alone; two earlier passes missed it because they ran only the two commands our own README documents, not the tools the bundled archive brings with it. The builder now reseals `checksums.sha256` after anonymising and writes an `ANONYMISATION.md` recording each altered file with both its released and its resealed digest, so the reseal hides nothing and the untouched files can still be checked against the public release. The archive now validates at exit 0, and the audit runs its validator as a fourth check.

**Rights are not verified, and cannot be by us.** The release carries no licence (publication-notes issue 7), the evidence archive embeds an inherited third-party benchmark archive, and TMLR applies CC BY 4.0 from submission onward. Until the owner settles this, **neither variant may ship**: `full` includes the archive, and even `scripts` describes it.

Three rows of that table — dependencies, links and the development/certification split — were originally written from inspection rather than measurement, and the link row was simply wrong as first written ("no external link in any packaged file"). `audit_supplement_contents.py` now re-derives all three from the built ZIP, and fails the `full` variant with exit status 1 on the certification finding above, so the claim cannot drift from the artifact again.

**Analysis.** The anonymity work found two leaks of opposite kinds. One was in someone else's file, in the single place a data package conventionally names its authors. The other was in our own file names, created by our own task numbering — a leak we introduced. Both would have survived any check short of scanning the actual bytes of the actual package.

The only strings matching a deliberately broad base64 pattern were SHA-256 digests in the manifests — with one exception, which is a finding.

### A malformed checksum in the released archive

`evidence/harness_scaling_curve/study_manifest.json` records:

| Field | Length |
|---|---|
| `canonical_report_sha256` | 64 |
| `run_ladder_py_sha256` | 64 |
| **`ladder_py_sha256`** | **65** |

A SHA-256 is 64 hex characters. This one has an extra character, so it cannot be a valid digest — and no file anywhere in the package hashes to any 64-character truncation of it. The file it names, `ladder.py`, is not in the release either, so the value cannot be checked against its subject in any case.

It is not a leak and not a credential; it is a provenance field that cannot do its job. It belongs with the metadata defects the publication notes already catalogue as known issues, and it is **not** among them — issue 1 covers version labels, not checksum validity. Reported here rather than corrected, because the released archive is the owner's and its manifest must not be edited to conceal a changed payload.

## Not done / limitations

- **Rights verification is outstanding** and is the gate on shipping.
- **The certification-item question (owner decision 6) is a second gate** on the `full` variant specifically. The audit exits non-zero on it deliberately, so no `full` package can be shipped while it is unanswered.
- No supplementary **PDF** is produced. TMLR permits a PDF or a ZIP; the material here is code and data, so a ZIP is the right form. If the owner wants a PDF summary as well, that is a small addition.
- The `full` variant's reproducibility covers the numerical claims DK-05 could reproduce. The item-family accuracies and two of the three curves cannot be reproduced by anyone with what exists.
- Both variants rebuild **byte-identically** across independent runs, confirmed by SHA-256.
- The package was tested on macOS with Python 3.12.6. It uses only the standard library and no OS-specific calls, but it has not been run on Linux or Windows.
